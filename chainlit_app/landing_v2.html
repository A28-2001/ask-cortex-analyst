The baseline is faster because it parses no semantic model. That is the whole trade, and it is the wrong side of it.

Nine of its thirteen failures share one root cause, and not one of them raised an error. With no documented valid values, the baseline guessed at how categories were stored: 'mid-market' for mid_market, 'At Risk' for at_risk, 'Anomalous' for flagged.

Every one of those filters is valid SQL. Every one silently returns zero rows or null. A business user reading the answer gets no signal that anything went wrong. That is exactly what the semantic model's documented sample values exist to prevent.

Method

What sits between the model and the warehouse

01

Warehouse

500 customers over 18 months of SaaS subscription data, modelled in dbt on Snowflake into tested marts: MRR movements, cohort retention, health scores, anomaly flags.

02

Semantic model

A YAML layer: logical tables, business synonyms, valid sample values for every category, verified example queries, and explicit rules on what to refuse.

03

Question to SQL

Cortex Analyst translates the question using that context. The baseline gets only raw table and column names, through Llama 3.3 70B on Groq.

04

Execution

A Chainlit app runs the SQL against Snowflake and renders the result, always showing the query. Zero row results get explained, not shown as an empty table.

Long results are capped and counted, never dumped.

Was churn anomalous in January 2025?

No matching data. January 2025 is the first month in the dataset, so there is not enough prior history to compute a rolling average or z score. Zero rows means the month cannot be evaluated, not that it was normal.

An empty result gets explained. This was a real failure in an earlier evaluation round, fixed at the semantic layer.

What is our gross margin?

Cannot answer. Gross margin is not defined in this warehouse. The data covers subscription revenue movements and customer health, with no cost of revenue to compute margin against.

An undefined metric is named as undefined instead of approximated.

Limitations

What this does not prove

01

The 100 percent is a post fix number. The first clean run scored 93.1 percent. I diagnosed three failure modes, a guardrail gap, an incomplete calculation, and a latent schema bug, fixed each, then re ran. Scoring perfectly on the set used to find the faults is a weaker claim than it looks.

02

The holdout carries the claim. Eight questions written after every fix was in place, never used for tuning, including a nonexistent customer ID and an undefined metric that never appeared in the original set. Eight of eight correct. Eight questions is still a small sample.

03

The fairest single pass comparison is 65.3 against 93.1. The baseline was run cold, once, with no iteration, by design. Comparing it to the fully iterated 100 would overstate the case.

04

One baseline model, one minimal prompt. A different model, or a hand engineered prompt that reinvents parts of a semantic layer, could score higher. This measures what a realistic naive setup gets you, not the ceiling of prompting.
